## Identity and independent digests

`SymbolCoordinate` contains product, SDK version, language, namespace, owner, member, ordered qualified erased parameter types and element kind. Its recoverable wire representation is `symbol:1:` plus eight URL-safe, unpadded UTF-8 base64 fields separated by dots: product, SDK version, language, namespace, owner, member, element kind and decimal parameter count, then that many parameter fields. Empty fields encode as an empty segment. Parsing rejects other versions, bad counts and noncanonical encodings. Constructor/method distinctions remain explicit; aliases never establish identity. See `fixtures/portable.properties` and `SymbolCoordinateTest` for a pinned wire value.

Multi-field SHA-256 uses UTF-8 byte length framing `<length>:<bytes>`; null is `-1:`, empty is `0:`. The domain tag is framed first. IDs use `identity/1/record` followed by entity type and ordered identity fields (coordinate wire, SDK version). Edge IDs use `identity/1/relationship`, SDK version, source record ID, SDK relationship type, target record ID and evidence. Source SHA-256 hashes original file bytes; `content/1` hashes the ordered canonical payload field stream; `javadoc-lexical/1` hashes profile plus sorted governed selection; `catalog-runtime/1` hashes schema version, identity version and interface version. These are independent dimensions; a content edit preserves a symbol ID and changes source/content/build input digests. Runtime changes alter runtime and complete build identity; a governance selection or profile change alters recipe and build identity. No timestamps, absolute roots or destination paths enter logical identity.

Partial member occurrence identity is `partial-occurrence/1` over source-relative path, element kind, name and original signature, rather than member enumeration position. Indistinguishable occurrences collide and invalidate the build even under COLLECT_AND_CONTINUE. Narrative IDs use `narrative/1`, product, SDK version, relative path and narrative kind. No guessed endpoint is selected for competing or absent evidence.

`build/1` hashes profile, recipe and runtime digests, optional training presence, explicit SDK binding and sorted root-role/relative-path/source-hash entries. The complete digest is the `b-<64 hex>` build ID. Model roots are ignored by the lexical profile; no model is required. Input/output roots are operational only. The shipped capability set is catalog and relationships; lexical search, examples/workflows, embeddings, vectors and activation remain explicitly skipped where unimplemented.

## Storage and validation

SQLite `user_version=1`, identity `identity/1`; `storage-schema.sql` describes the relational contract. Existing schema 0, unknown/future schema and incompatible identity require rebuild. A read-only preflight runs before writable connections or DDL and leaves unsupported file bytes unchanged. There is no in-place migration or automatic deletion. Tables preserve the existing catalog/edge/reference-evidence families; knowledge dependencies are separately versioned (`knowledge-dependency/1`) and never silently enter SDK traversal.

Records separate physical record type from AUTHORITATIVE_FACT, EXPERT_APPROVED_PRACTICE, RECIPE and CANDIDATE_LEARNING. Candidates cannot activate, including candidates falsely marked approved. Approved practices/recipes require owner, provenance, approval evidence and applicable product/SDK constraints. Required dependencies must exist, match scope, target usable approved knowledge and be acyclic; optional dependencies do not create required-cycle failures. Ordinary unresolved source links are legal evidence. The current SQLite capabilities reject nonempty knowledge/dependency tables until their owning adapters are implemented, rather than certifying unread data.

`BuildValidator`/`StandardBuildValidator` owns one sorted reason set for CLI, startup, activation, reload, rollback and restore. Existing CLI and pinned serving paths invoke it; lifecycle operations not present in this repository must call the same port when implemented. The existing CLI wiring is the bootstrap seam; no new bootstrap module or lifecycle orchestrator is introduced. Persisted schema/identity/runtime/build/SDK/profile/recipe/capability metadata are read and checked, not substituted with expected constants. Binding a manifest compares existing metadata and cannot overwrite it on resume. Invalidating failures are sticky metadata. A completed resume revalidates persisted metadata. Unsupported stages cannot count as completed activation, and aborted ingestion raises an unsuccessful CLI result.

Validation bounds apply before TEXT materialization: 100,000 catalog records, 1 MiB per stored field, 16 MiB aggregate catalog TEXT; metadata rows are bounded to one row/table and 2 KiB/field. Pinned SQLite snapshots span the metadata-only `octet_length` pass and content reads. SDK traversal retains its stricter per-response and adjacency guards. Domain dependency validation caps 200,000 edges. These are fail-closed admission limits, not claims of unlimited corpus support.

## Durable content handoff

`DocumentationPayload` is a contract only; Stories 2.9-2.11 implement extraction and storage. Stable record IDs associate API or symbol-less narrative records atomically with a complete payload. Ordered sections contain paragraph, code, table, list and labeled note blocks, preserved original links, scoped locators, and derived searchable text. Tables preserve ordered headers/rows/cells; lists preserve ordered/unordered state and nested text/children. Do not replace structured cells/items with a flattened string. Maximum nesting is 32, sections 256, blocks 4096 and canonical content bytes 1 MiB. Unsupported format, excessive work or oversize content must fail explicitly; no silent dropping.

Typed source locators carry an actual relative path, optional actual anchor, optional inclusive 1-based line range and optional curated section. SOURCE without an anchor is legal and truthful. ABSENT requires a reason and has no fabricated anchor/range/section. EXTERNAL preserves the original external target. Legacy catalog join anchors are lookup metadata, never proof that a citation exists. Source hash, complete document content hash and section-page content hash are distinct. Canonical payload framing includes section/block counts, all structural data, original links and locator fields, so boundary/ordering changes affect content hashes.

`DocumentationStore.putAtomically` either stores metadata+payload together, reports identical, or reports an identity clash without partial changes. Bounded read/enumeration limit is 1..50. `SectionPage` carries record ID, complete-document hash, selected-page hash, sections and continuation; a section page never pretends to contain the entire document. Reads/restarts retain stable association. Page/record/section coverage uses discovered/completed/excluded/failed and an optional expected denominator; completed+excluded+failed cannot exceed discovered. Unknown counts/denominators remain absent. The current report exposes unknown coverage explicitly; Story 2.11 supplies reconciled instrumentation.

## Six read-only tools

Each `<tool>.request.schema.json` and `<tool>.response.schema.json` is an exact JSON Schema 2020-12 contract with no additional properties; `<tool>.example.json` is a synthetic, explicitly incomplete specimen. `common.schema.json` defines shared proof/error/citation/locator/record contracts. These are future handler contracts, not implemented endpoints.

| Tool | Request | Data |
| --- | --- | --- |
| search_knowledge | query, kind filters, LEXICAL or deterministic BROWSE | ordered hits |
| resolve_symbol | symbol, alias inclusion | exact/ambiguous matches; aliases never establish identity |
| get_record | stable record ID batch, section IDs, content inclusion | records, document hash, page hash, bounded sections |
| get_relationships | seed, explicitly SDK or KNOWLEDGE_DEPENDENCY family, direction, direct/recursive bounds | nodes and typed evidence edges |
| check_symbols | ordered symbol batch | one visible verdict per input; selected ID only for exact proof |
| index_status | coverage inclusion | visible build state/profile/capabilities/ratification |

SDK version is explicit or bound by operator configuration before normalization; one immutable build is pinned for the request. Cross-version combined queries are unsupported. Results retain SDK/build, normalized trace, proof, count relation, coverage reason, empty reason, truncation and continuation. EXACT count means a proven complete admitted window; LOWER_BOUND means a bounded incomplete exploration; UNKNOWN carries null. Empty results never imply an API does not exist outside the bound scope. Batch results preserve input order and an item-level verdict for every admitted input; aggregate payload admission must not silently discard trailing verdicts.

Content snippets/sections require truthful typed citations. Verdicts and index status remain visible with no content citations; citations are not required to state unknown/ambiguous/not-applicable status. A match score cannot upgrade proof. Required record metadata carries governance and applicability separately from source citations. Unknown SDK, missing build, incompatible build, malformed request/cursor, oversize payload, work/deadline/cancellation and internal errors use the shared typed codes. An error returns null data and cannot claim exact catalog proof; per-item unknown verdicts are successful admitted responses.

Default page is 10, cap 50; batch cap 50; request/query UTF-8 key cap 2 KiB, cursor 4 KiB, serialized response cap 1 MiB. Default candidates/work/time are 1000/5000/1000 ms; caps 10000/50000/5000 ms. Reserve response metadata and charge candidate/scan work before intermediate materialization or filtering; stop with truthful truncation or typed error. Check serialized UTF-8 bytes before delivery. Unbounded total-count scans are forbidden. Content that does not fit must use bounded sections+continuation or PAYLOAD_TOO_LARGE, never truncation disguised as complete content.

Traversal defaults/caps: depth 3/8 (DIRECT forces one hop), visited nodes 1000/10000, adjacency rows 5000/50000, result items 1000/10000, page 10/50, execution 1/5 s and SQL steps 1m/10m. Deterministic cycle-safe traversal charges duplicate adjacency reads before deduplication. Cursor bindings include contract/identity versions, tool, normalized query, all filters/order/work limits, SDK and immutable build. Tokens are authenticated with a runtime secret, finite, and rejected before graph work on query/build/version/key mismatch. No administrative mutation tools are exposed.

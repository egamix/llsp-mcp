# API documentation storage — schema/2

Story 2.9 adoption authorizes identity/1, DocumentationPayload, typed locators, the bounded DocumentationStore port and this schema extension. Stable identity and read-tools/2 guidance are unchanged. Earlier schemas require a rebuild: read-only preflight rejects them before DDL and preserves the file. Other interface, evaluation and release approvals remain pending.

`CatalogStore.putDocumented` commits a catalog tuple, full knowledge metadata, document hash/source hash and ordered sections in one SQLite transaction. `DocumentationStore.putAtomically` derives the equivalent tuple from the API coordinate. Identical retries are no-ops; changed identity-associated metadata, provenance or content returns IDENTITY_CLASH without replacing the existing association. Content-only edits belong to a new content-addressed build, retaining the logical record ID.

Documentation payloads retain at most 256 sections, 4096 blocks and 1 MiB of canonical UTF-8 field data. Each section BLOB encodes `DocumentationPayload.canonicalFields([section])`: big-endian signed 32-bit field count, followed by signed 32-bit byte lengths and UTF-8 bytes; -1 denotes null. Noncanonical encodings, invalid counts, trailing bytes and invalid structures are rejected. Count is at most 65536. Total document section encoding is at most 1,310,724 bytes, bounding framing overhead independently of the 1 MiB canonical data limit. Metadata uses the same bounded framing over the 18 knowledge-table columns in schema order. Applicability is base64 of framed product, scope, version count, versions, then conditions. Metadata is checked against the relational columns and reconstructed domain contracts at validation.

Sections store independent content hashes. Documents retain the original source-byte SHA-256 and the complete ordered document content hash; section pages compute their own ordered page hash. These hashes never define stable symbol identity. SQLite reads select byte lengths before allocating content and validate selected section hashes. CLI validation and pinned startup validate complete document hashes and associations. Source HTML is never read during fetch.

Reads require the actual build ID and source SDK, page limits 1..50, and zero-based section offsets. Missing IDs return empty; wrong build/source or invalid offsets/limits are rejected. Continuation carries the next section offset and a domain-separated scope digest binding record, build, source SDK, page limit, schema and runtime. The string-continuation overload rejects malformed/rebound tokens before a content read. These are continuation integrity markers, not authorization credentials. Enumeration orders stable IDs and uses an exclusive `afterId`. A page whose encoded sections exceed 1 MiB minus 1024 bytes is explicitly rejected; callers can request fewer sections. This domain adapter does not serialize read-tools response envelopes.

Production manifests advertise `api-documentation`, `catalog`, `relationships`; validation requires content for every catalog row. Explicit catalog/relationship-only synthetic or lower-level builds retain their declared capabilities. Unsupported narratives, practices, recipes and curated dependencies cannot pass API-content validation. Extraction assembles normalized semantic blocks here; full owned block/link fidelity is Story 2.10 and coverage is Story 2.11.
